# Универсальная платформа ассистента

## What This Is

Платформа персонального ИИ-ассистента из двух репозиториев: Antigravity Studio (`/opt/chat-app`: FastAPI, веб-студия, Security Tile, дашборд задач) и Assistant Core (`/opt/assistant-core`: демон с Telegram-ботом, секретарь, методист, коннекторы). Сегодня она целиком настроена под одного владельца — Попова Д.А. (доцент кафедры физики ГУАП и сотрудник Тидекс). Проект переносит весь профиль владельца из кода в данные (персона, рабочие пространства, привязки коннекторов), чтобы платформой мог пользоваться любой специалист, а владелец продолжил работать ровно как раньше. Новая возможность: секретарь по коммитам из любого числа git-репозиториев оценивает ход проектов и обновляет их дашборды в Notion.

## Core Value

Профиль владельца целиком живёт в данных, а платформа работает для любой персоны — без регрессии поведения и без ослабления HITL-подтверждений и air-gap-изоляции NDA.

## Success Metric (метрика завершения проекта)

Профиль Попова Д.А. (ГУАП / Тидекс) полностью перенесён в данные: в коде chat-app и assistant-core не осталось хардкода ГУАП, Тидекс, ФИО, персональных путей и аккаунтов; персона по умолчанию работает как раньше; pytest проходит на 100% в обоих репозиториях.

Тест второй синтетической персоны НЕ является метрикой завершения. Это страховка, обязательная в критериях приёмки Фаз 0 (каркас), 2 и 5.

## Constraints

- **Среда выполнения**: существующий VPS — Python 3.12, systemd, 2 ГБ RAM + 4.5 ГБ swap; новые тяжёлые сервисы (внешний брокер, Redis, внешняя БД) запрещены — ресурсов не хватит.
- **Тесты**: 100% pytest в ОБОИХ репозиториях на каждом шаге — `/opt/chat-app/backend/.venv/bin/pytest backend/tests` и `/opt/assistant-core/.venv/bin/pytest /opt/assistant-core/tests`; существующие тесты не удаляются и не ослабляются.
- **HITL**: любое деструктивное действие (стирание памяти, удаление данных, выставление оценок, DELETE-эндпоинты) требует подтверждения человека; записи в Notion — тоже через HITL-примитив.
- **Air-gap NDA**: содержимое рабочих пространств `restricted_nda` (код, git-активность, тело и вложения NDA-почты) не уходит в LLM, публичные репозитории, логи и контекст агентов публичных проектов.
- **Async-first**: весь ввод-вывод — `aiosqlite`, `httpx`/`aiohttp`.
- **KISS и YAGNI**: типизированные dataclass и Pydantic-модели, без избыточных абстракций.
- **Язык**: пользовательский вывод (чат, Telegram, UI) строго на русском; код, комментарии и коммиты — на английском или русском.
- **Секреты**: ключи, токены, пароли, e-mail и телефоны не попадают в артефакты планирования, код и коммиты; файлы `.env`, `credentials.json`, `token.json` и systemd-юниты агенты не читают.
- **Коммиты**: атомарные, с возможностью revert; без ручного прогона тестов фаза не считается завершённой.
- **Node/Claude**: команды Node и Claude запускать с `NODE_OPTIONS="--max-old-space-size=1536"`.
- **Заморозка**: сервисы не запускаются без явного решения владельца; проверка фаз опирается на pytest и локальные прогоны.

## Решения владельца (LOCKED)

ADR в наборе документов нет. Решения W1–W10 приняты владельцем 2026-10-01 и имеют приоритет над автоматическим precedence документов и над любыми другими артефактами. Менять их можно только по явному решению владельца. Источник: `.planning/intel/user-resolutions.md`.

### W1. Модель git-аккаунтов — LOCKED
У владельца может быть любое число репозиториев под разными аккаунтами в разных git-сервисах (GitHub, GitLab и др.). Платформа подключает их предпочтительно по SSH. Цель — секретарь по коммитам определяет ход выполнения проекта и управляет дашбордами проектов в Notion.
Следствия: SSH-профиль (хост, аккаунт, alias ключа) — данные рабочего пространства; новый порт git-источника (`git_source`, только чтение); связь «репозиторий → проект Notion» — данные; изменения дашбордов Notion идут через HITL; git-активность `restricted_nda` не уходит в LLM. Реализация — Фаза 6.

### W2. Рабочие пространства по умолчанию — LOCKED
Персона по умолчанию содержит все 4 рабочих пространства: chat-app (public), assistant-core (public), кафедра физики (internal), Тидекс (restricted_nda) — идентично текущему `PROJECTS_REGISTRY`. Раздел 3.1 blueprint, где было только 2, исправлен. Каталоги кафедры и Тидекс на сервере отсутствуют (показываются как air-gap). Список рабочих пространств одновременно является списком репозиториев, отслеживаемых секретарём по коммитам.

### W3. Правила NDA — LOCKED
NDA-правила переносятся из кода в данные рабочего пространства (`forbidden_remote_substrings`, `forbidden_keywords`, `clearance`). Обязателен тест эквивалентности: каждая сегодняшняя NDA-проверка воспроизводится из данных без ослабления блокировки. Реализация — Фаза 2 (затем перепроверка в Фазе 3).

### W4. Уровни допуска — LOCKED
Три уровня: `public`, `internal`, `restricted_nda`. Для public и internal — проверка секретов и запрещённых файлов; для restricted_nda дополнительно — проверка remote, запрещённых слов и запрет отправки содержимого в LLM.

### W5. Security Shield — LOCKED
Одна общая библиотека проверок (секреты, запрещённые файлы, NDA-правила из данных). `scripts/security_shield.py` — тонкая CLI-обёртка над ней; Security Tile использует ту же библиотеку. Отдельная небольшая задача — установить проверку как pre-commit hook. Факт на 2026-10-01: pre-commit hook и CI отсутствуют в обоих репозиториях. Реализация — Фаза 3.

### W6. Раскладка каталогов — LOCKED
Фактические пути хранятся как данные в настройках рабочего пространства, обязательной раскладки нет. Репозитории не переносятся, systemd-сервисы не меняются. Раскладка `/opt/personal/*` из MULTI_PROJECT отменена.

### W7. Notion — LOCKED
Дашборды проектов в Notion — функция платформы: Notion становится коннектором, список проектов задаётся в персоне, у репозитория/рабочего пространства есть связь с проектом Notion, секретарь обновляет дашборды по git-активности. «Рельсы разработки» (`scripts/notion_dev.py`, сессионный след агентов) — инструмент разработки вне миграции; сломанный импорт в chat-app-копии чинится отдельной мелкой задачей. Реализация — Фаза 6.

### W8. Источники расписания — LOCKED
Роли разделены, на одну роль допускается несколько привязок: `schedule_source` — откуда берётся расписание (в персоне по умолчанию `ScheduleParser`, сайт расписания вуза, а не LMS); `calendar_sync` — куда синхронизировать (Google Calendar — приёмник, не источник); `lms` — задания LMS (`GuapLmsClient`, личный кабинет). Раздел 3.1/2.2 blueprint исправлен.

### W9. Развязка БД (Фаза 3) — LOCKED
Одна общая SQLite с явным владельцем схемы: схема и миграции — в общей библиотеке (не ad hoc в `assistant-core/src/storage/db.py`); путь к БД — из настроек (убрать хардкод `SQLITE_DB_PATH` в `chat-app`); включить WAL; тесты chat-app создают временную пустую БД через общую схему и не зависят от `/opt/assistant-core`. Межпроцессная шина событий не нужна (шина внутрипроцессная); двойная запись не нужна. Варианты blueprint (две БД с синхронизацией; read-only реплика) отклонены.

### W10. Проверка переноса промптов (Фаза 2) — LOCKED
До переноса фиксируется точный текст всех системных промптов (секретарь, маршрутизатор, методист); после переноса в Jinja2-шаблоны тест рендерит шаблон с персоной по умолчанию и сравнивает с сохранённым текстом символ в символ. Golden-набор ответов LLM не нужен. Снимок — пререквизит Фазы 2 и часть её Definition of Done.
