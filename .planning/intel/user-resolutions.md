# Решения пользователя по конфликтам импорта

Источник: `.planning/INGEST-CONFLICTS.md` (10 WARNING). Решения приняты пользователем 2026-10-01 через опросы. Имеют приоритет над автоматическим precedence.

## W1. Модель аккаунтов Git — РЕШЕНО (новое требование)

Решение пользователя: у пользователя может быть любое число репозиториев под разными аккаунтами в разных git-сервисах (GitHub, GitLab и др.). Платформа должна позволять подключать такие репозитории, предпочтительно по SSH как наиболее универсальному каналу. Цель — секретарь по коммитам определяет ход выполнения проекта и управляет дашбордами проектов в Notion.

Следствия для планирования:
- Аккаунт/SSH-профиль — данные (git-хост, аккаунт, SSH-ключ/alias) у рабочего пространства/репозитория, а не два жёстко заданных аккаунта.
- Новый порт: источник git-активности (`BaseGitSourceProvider` или аналог) — чтение коммитов по SSH для оценки прогресса проекта.
- Связь «репозиторий → проект в Notion» как данные; Notion становится коннектором с конфигурируемым списком проектов (влияет на W7).
- Действия, меняющие дашборды Notion, подпадают под HITL по правилам CLAUDE.md, если они деструктивны.
- Изоляция NDA сохраняется: git-активность restricted_nda-репозиториев не уходит в LLM без разрешения правил допуска.

## W2. Список проектов в Security Tile — РЕШЕНО

Персона по умолчанию содержит все 4 рабочих пространства: chat-app (public), assistant-core (public), кафедра физики (internal), Тидекс (restricted_nda) — поведение идентично текущему `PROJECTS_REGISTRY`. Блюпринт (разд. 3.1) исправить: там ошибочно только 2. Обоснование: на сервере реально существуют только `/opt/chat-app` и `/opt/assistant-core`; каталоги кафедры и Тидекса отсутствуют (показываются как air-gap). Список рабочих пространств одновременно является списком репозиториев, отслеживаемых секретарём по коммитам (см. W1).

## W6. Раскладка каталогов — РЕШЕНО

Фактические пути как данные: путь хранится в настройках рабочего пространства, обязательной раскладки нет. Репозитории не переносятся, systemd-сервисы не меняются. Старая раскладка `/opt/personal/*` из MULTI отменена.

## W3. Правила NDA — РЕШЕНО

Перенос NDA-правил из кода в данные рабочего пространства (`forbidden_remote_substrings`, `forbidden_keywords`, `clearance`). Обязателен тест эквивалентности: каждая сегодняшняя NDA-проверка воспроизводится из persona.yaml без ослабления блокировки.

## W4. Уровни допуска — РЕШЕНО

Три уровня: `public`, `internal`, `restricted_nda`. public и internal — проверка секретов и запрещённых файлов; restricted_nda — дополнительно проверка remote, запрещённых слов и запрет отправки содержимого в LLM.

## W5. Security Shield — РЕШЕНО

Одна общая библиотека проверок (секреты, запрещённые файлы, NDA-правила из данных рабочего пространства). `scripts/security_shield.py` становится тонкой CLI-обёрткой над ней; Security Tile использует ту же библиотеку. Отдельная небольшая задача: установить проверку как pre-commit hook. Факт на 2026-10-01: pre-commit hook и CI сейчас отсутствуют в обоих репозиториях, скрипт запускается только вручную.

## W7. Notion — РЕШЕНО

Дашборды проектов в Notion — функция платформы: Notion становится коннектором, список проектов задаётся в настройках персоны, у репозитория/рабочего пространства есть связь с проектом Notion, секретарь обновляет дашборды по git-активности (см. W1). «Рельсы разработки» (`scripts/notion_dev.py`, сессионный след агентов) — инструмент разработки, вне scope миграции; сломанный импорт в chat-app-копии чинится отдельной мелкой задачей.

## W8. Источники расписания — РЕШЕНО

Роли разделены, на одну роль допускается несколько привязок:
- `schedule_source` — откуда берётся расписание: в персоне по умолчанию это `ScheduleParser` (сайт расписания вуза), а не LMS.
- `calendar_sync` — куда синхронизировать: Google Calendar — приёмник, не источник.
- `lms` — задания LMS: `GuapLmsClient` (личный кабинет).
Блюпринт (разд. 3.1, 2.2) исправить: там роль schedule ошибочно привязана к `guap_lms`. Проверено по `src/main.py` и `src/parser/schedule_parser.py` в assistant-core.

## W9. Развязка БД (Фаза 3) — РЕШЕНО (третий вариант, не из блюпринта)

Одна общая SQLite-база с явным владельцем схемы:
- схема и миграции — в общей библиотеке (не создаются ad hoc в `assistant-core/src/storage/db.py`);
- путь к базе — из настроек (env/конфиг), убрать хардкод `SQLITE_DB_PATH` в `chat-app/backend/app/core/config.py`;
- включить режим WAL для безопасной одновременной записи двух процессов;
- тесты chat-app создают временную пустую базу через общую схему и не зависят от `/opt/assistant-core`.
Межпроцессная шина событий в Фазе 3 не нужна (шина остаётся внутрипроцессной). Варианты блюпринта (две БД с синхронизацией; read-only реплика) отклонены.

Факты (проверено 2026-10-01): оба процесса пишут в `tasks`, `reminders`, `projects`, `documents`; остальные ~20 таблиц пишет только assistant-core; WAL не включён.

## W10. Проверка переноса промптов (Фаза 2) — РЕШЕНО

Снимок промптов: до переноса фиксируется точный текст всех системных промптов (секретарь, маршрутизатор, методист); после переноса в Jinja2-шаблоны тест рендерит шаблон с персоной по умолчанию и сравнивает с сохранённым текстом символ в символ. Golden-набор ответов LLM не нужен. Снимок — пререквизит Фазы 2 и часть её DoD.

## Параметры проекта (вне WARNING) — РЕШЕНО

- Название проекта: «Универсальная платформа ассистента».
- Метрика завершения: профиль Попова Д.А. полностью перенесён в данные — в коде (chat-app и assistant-core) не осталось хардкода ГУАП/Тидекс/ФИО/персональных путей и аккаунтов; персона по умолчанию работает как раньше; 100% pytest.
- Тест со второй синтетической персоной СОХРАНЯЕТСЯ как страховка в критериях приёмки Фаз 0 (каркас), 2 и 5 — он не является метрикой завершения, но обязателен в DoD этих фаз.
- Целевая среда: существующий VPS (Python 3.12, systemd, 2 ГБ RAM + 4.5 ГБ swap), без новых тяжёлых сервисов.
- Состояние на старте: проект заморожен 2026-10-01 — сервисы `assistant-worker`, `chat-app`, `dev-bridge` остановлены и сняты с автозапуска.
