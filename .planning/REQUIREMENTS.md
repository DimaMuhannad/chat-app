# Requirements: Универсальная платформа ассистента

**Defined:** 2026-10-01
**Core Value:** Профиль владельца целиком живёт в данных, а платформа работает для любой персоны — без регрессии поведения и без ослабления HITL-подтверждений и air-gap-изоляции NDA.

Обозначения репозиториев: `chat-app` = `/opt/chat-app`, `assistant-core` = `/opt/assistant-core`. В квадратных скобках у каждого требования указано, какие репозитории оно затрагивает.

Источники: `docs/UNIVERSAL_ARCHITECTURE_BLUEPRINT.md` (разд. 3–5), решения владельца W1–W10 (`.planning/intel/user-resolutions.md`), карта кодовой базы `.planning/codebase/`.

## Сквозные критерии приёмки (входят в приёмку КАЖДОЙ фазы)

Это не отдельные требования, а гейт на каждой фазе (см. ROADMAP.md):

1. 100% pytest в обоих репозиториях: `/opt/chat-app/backend/.venv/bin/pytest backend/tests` и `/opt/assistant-core/.venv/bin/pytest /opt/assistant-core/tests`.
2. Атомарные коммиты с возможностью revert; существующие тесты не удаляются и не ослабляются.
3. Персона по умолчанию ведёт себя как раньше (единственное осознанное изменение поведения — закрытие DELETE без подтверждения в Фазе 5).
4. Второй синтетической персоны тест входит в набор с Фазы 1 и явно перечислен в DoD Фаз 1, 3 и 6.
5. HITL для деструктивных действий, air-gap для NDA, async-first, KISS/YAGNI — жёсткие ограничения.
6. Сервисы остаются остановленными, пока владелец явно не решит иначе; проверка опирается на тесты.
7. В артефактах и коде нет секретов, e-mail, телефонов и конфиденциальных сведений о компании.

### Страховочная сеть (FND) — Фаза 1

- [x] **FND-01** [chat-app + assistant-core]: Зафиксирован baseline тестов: для каждого репозитория — команда запуска, число тестов, статус каждого, дата. Прогон chat-app выполняется на копии БД или временной БД и не пишет в боевую `assistant.db`. Если на старте есть падающие тесты — они устранены без ослабления ассертов либо явно вынесены владельцу на решение.
- [x] **FND-02** [assistant-core + chat-app]: Настроен контракт import-linter: use-cases (`brain`) не импортируют адаптеры (коннекторы, календарь, парсеры, отправка); backend chat-app не импортирует внутренние модули assistant-core. Существующие нарушения перечислены явным списком `ignore_imports` (долг), который может только убывать. Контракт доказанно падает на намеренном нарушении.
- [x] **FND-03** [chat-app + assistant-core]: Каркас второй синтетической персоны: фикстура-заглушка, отличающаяся от персоны по умолчанию во всех идентифицирующих полях, и тесты каркаса, которые проходят уже сейчас; проверки, ожидающие Фазы 3, перечислены явно (без xfail и без ослабления).
- [x] **FND-04** [chat-app + assistant-core]: Единая локальная команда-гейт (скрипт, без внешнего CI-сервиса) запускает оба pytest, import-linter и `scripts/security_shield.py` и печатает итог по каждому репозиторию. Правило «100% pytest на каждом шаге, атомарный коммит, revert» зафиксировано документом baseline.

### База данных и безопасность (DAT, SEC) — Фаза 4

- [ ] **DAT-01** [chat-app + assistant-core]: Схема БД и миграции принадлежат общей библиотеке (явный владелец схемы), а не создаются ad hoc в `assistant-core/src/storage/db.py`. Версия схемы хранится в БД; на пустой БД миграции строят схему полностью; существующая боевая БД распознаётся как базовая версия без изменения данных.
- [ ] **DAT-02** [chat-app + assistant-core]: Путь к БД берётся из настроек (env/конфиг) в обоих процессах; хардкод `SQLITE_DB_PATH` на `/opt/assistant-core/data/assistant.db` в `chat-app/backend/app/core/config.py` убран. Прод-значение задаётся окружением сервисов — правка окружения systemd является шагом разморозки владельца.
- [ ] **DAT-03** [chat-app + assistant-core]: Для общей БД включены WAL и `busy_timeout`; два процесса одновременно пишут в `tasks`, `reminders`, `projects`, `documents` без ошибок блокировки (тест конкурентной записи).
- [ ] **DAT-04** [chat-app]: Тесты chat-app создают временную пустую БД через общую схему, данные подготавливают фикстуры, ассерты не ослаблены; `pytest backend/tests` проходит без доступа к `/opt/assistant-core`.
- [ ] **SEC-01** [chat-app + assistant-core]: Одна общая библиотека проверок безопасности: `SECRET_PATTERNS` (включая Generic Bearer), `FORBIDDEN_FILES`, `run_cmd()`, NDA-правила из данных рабочего пространства; её импортируют Security Tile (chat-app) и assistant-core. Тест эквивалентности NDA из PER-04 перезапускается против библиотеки.
- [ ] **SEC-02** [chat-app + assistant-core]: `scripts/security_shield.py` в обоих репозиториях — тонкая CLI-обёртка над библиотекой; тест подтверждает отсутствие дрейфа (одинаковый результат Web-аудита и shield на общем наборе синтетических фикстур).
- [ ] **SEC-03** [chat-app + assistant-core]: pre-commit hook с проверкой установлен в обоих репозиториях воспроизводимо (hook и скрипт установки хранятся в репозитории) и блокирует коммит с синтетическим «секретом».

### Единый HITL (HIT) — Фаза 5

- [ ] **HIT-01** [chat-app + assistant-core]: Порт `ConfirmationStore`, `PendingConfirmation`, декоратор `@requires_confirmation` и единая точка `resume_action` в общей библиотеке; таблица `pending_confirmations` добавлена миграцией.
- [ ] **HIT-02** [assistant-core]: Telegram-flow (`clear_dialog`, выставление оценок `submit_grade`, прочие деструктивные действия) переведён на примитив без изменения UX; `test_hitl_safety_guardrails.py` и `test_bot_group_isolation.py` проходят без изменения ассертов.
- [ ] **HIT-03** [chat-app]: Все DELETE-эндпоинты chat-app (`projects`, `documents`, `tasks`, `reminders`) используют примитив: запрос без подтверждения возвращает 409 и создаёт запись в `pending_confirmations`, данные не удаляются; владельцу уходит карточка «Да / Отмена» в Telegram (проверка `allowed_user_id`), подтвердить или отклонить можно ТОЛЬКО оттуда (решение владельца 2026-10-01). Web API подтверждать не может; допустим лишь `GET /api/v1/confirmations/{id}` для показа статуса «ожидает подтверждения». Новый `test_web_hitl_guardrails.py`; существующие CRUD-тесты переведены на двухшаговый поток без ослабления силы проверки.
- [ ] **HIT-04** [chat-app + assistant-core]: Подтверждение приходит из авторизованного канала (Telegram владельца либо токен подтверждения, выданный интерфейсом; точный канал фиксируется в discuss-phase 5): анонимный HTTP-запрос не может подтвердить собственный DELETE. Веб-интерфейс показывает состояние «ожидает подтверждения» вместо ложного «удалено».

### Мультитенантность и завершение (ISO, FIN) — Фаза 6

- [ ] **ISO-01** [assistant-core]: `key_rotator.py` не мутирует глобальный `config.GEMINI_API_KEY`; ключи принадлежат контексту персоны (явная передача или `contextvars`); `test_key_rotator.py` проходит.
- [ ] **ISO-02** [assistant-core]: `WorkspaceScope` (air-gap) внутри assistant-core: содержимое рабочих пространств `restricted_nda`, включая тело и вложения NDA-почты (`EmailMessage`), никогда не передаётся в LLM; метаданные обрабатываются только локальным кодом. Проверяется тестом с «ловушкой» вместо LLM-клиента.
- [ ] **ISO-03** [chat-app + assistant-core]: Zero-Trust scopes: коннектор объявляет `required_scopes`, персона выдаёт `scopes`; ядро отказывается поднимать коннектор без выданного scope; процесс chat-app не держит учётные данные LMS (проверяемый тест).
- [ ] **ISO-04** [chat-app + assistant-core]: Интеграционный тест одновременно инстанцирует персону по умолчанию и вторую синтетическую персону и подтверждает отсутствие cross-talk (ключи, кэши, рабочие пространства, привязки коннекторов, подтверждения).
- [ ] **FIN-01** [chat-app + assistant-core]: Метрика завершения подтверждена: сканер хардкода (PER-08) работает с пустым allowlist — в коде обоих репозиториев нет ГУАП, Тидекс, ФИО, персональных путей и аккаунтов вне данных персоны; персона по умолчанию ведёт себя как раньше; 100% pytest.

### Git-источники и Notion (GIT, NTN) — Фаза 7

- [ ] **GIT-01** [assistant-core]: Порт `BaseGitSourceProvider` (async, только чтение: репозитории, коммиты начиная с даты, ветки) и реализация `ssh_git`: чтение по SSH с любого git-хоста (GitHub, GitLab и др.); scope `git.read`; push и изменение репозиториев невозможны.
- [ ] **GIT-02** [assistant-core]: Подключение любого числа репозиториев — только данными рабочего пространства (`git: host, account, ssh_alias, remote`) без правки кода; допускается несколько аккаунтов и хостов. Приватные ключи не хранятся в персоне и БД (только alias). Рабочие пространства без remote или с отсутствующим каталогом пропускаются с видимым статусом.
- [ ] **GIT-03** [assistant-core]: Секретарь формирует оценку хода проекта по коммитам (активность за период, что сделано, застой) для репозиториев public и internal; пользовательский вывод на русском.
- [ ] **GIT-04** [assistant-core]: Для репозиториев `restricted_nda` содержимое git-активности (сообщения коммитов, диффы, имена файлов) не передаётся в LLM (через `WorkspaceScope`). В Notion по ним передаются ТОЛЬКО обезличенные агрегаты — число коммитов и даты; запрещены текст сообщений, имена файлов, названия веток, авторы, диффы (решение владельца 2026-10-01). Проверяется тестом с «ловушкой» LLM-клиента и тестом, что полезная нагрузка записи в Notion для `restricted_nda` содержит только разрешённые поля.
- [ ] **NTN-01** [assistant-core]: Коннектор Notion (на базе существующего `src/connectors/notion`) с конфигурируемым списком проектов в персоне; связь «рабочее пространство/репозиторий → проект Notion» (`notion_project`) — данные.
- [ ] **NTN-02** [assistant-core]: Обновление дашборда проекта в Notion по git-активности: секретарь предлагает изменение, запись происходит только после подтверждения владельцем через HITL-примитив Фазы 5 (подтверждение может быть пакетным, один дайджест на цикл). Отклонение ничего не пишет; повторный цикл не создаёт дублей; сбой SSH или Notion не роняет демон и виден в статусе.

## Out of Scope

Явно исключено; задокументировано, чтобы не расползался объём.

| Feature | Reason |
|---------|--------|
| Две БД с синхронизацией событиями; read-only реплика | Отклонено решением W9: одна общая БД с явным владельцем схемы |
| Межпроцессная шина событий, внешний брокер, Redis | Не нужны после W9; новые тяжёлые сервисы на VPS запрещены |
| Двойная запись в переходный период | Снята решением W9 вместе с разделением БД |
| Golden-набор ответов LLM | Отклонён решением W10: снимок текста промптов и посимвольное сравнение |
| Notion «рельсы разработки» (`scripts/notion_dev.py`, сессионный след агентов) | Инструмент разработки, вне миграции (W7); чинится отдельной мелкой задачей |
| Перенос репозиториев в `/opt/personal/*`; изменение systemd-сервисов | Отменено решением W6: пути — данные |
| Ровно два git-аккаунта, фиксированный includeIf | Заменено моделью «любое число репозиториев» (W1) |
| Запись в git-репозитории (push, ветки, коммиты) | Платформа читает активность, не изменяет репозитории |
| Ротация API-ключа dev-bridge | Решение владельца: не ротировать; экспозиция только фиксируется |
